# Zero-Input AI Onboarding — Design Doc

**Ticket:** aexa-frontend#96
**Status:** Needs product decision (this doc is the input to that decision)
**Author:** Design pass by Claude, grounded in current aexa-frontend/aexa-server/aexa-ai code, the Fullbloom precedent, the CDC spec, and external research
**Date:** 2026-07-21

---

## Problem Statement

Today, organization creation in Qiyrix is a stub. `aexa-frontend/src/dashboard/admin/organizations/AdminOrganization.tsx` renders a table of **hardcoded dummy organizations** and a "Create New Organization" modal that collects `org_name`, `userName`, `email`, `password`, then does `setTimeout(() => alert(...), 800)` — it never calls a real API. There is no `POST /organization` route anywhere in `aexa-server/src/app/modules` at all; grepping the whole modules tree for organization-creation logic returns nothing. So the *actual* current state is: there is no working way to create an organization in Qiyrix, admin-side or otherwise, and there is no `analyzeCompany`/onboarding-wizard equivalent, confirming the ticket's premise.

Once an org does get created (by whatever mechanism), it starts completely empty: no Sites, no Risks, no KRIs, no Alerts. Every one of those has to be hand-entered before the platform produces any value — a cold-start problem that is especially costly for a GRC tool, where the value proposition is breadth of coverage (risk taxonomy, KRI thresholds, alert wiring) that most buyers don't want to configure by hand on day one.

Fullbloom (the earlier Supabase build of the same product) solved this with a "Zero-Input Intelligence" onboarding page: company name in, fully-populated org (sites, risks, KRIs, alerts, audit plan, compliance register) out, in under a minute. The CDC spec treats this as the platform's core differentiator and Phase 1 of the roadmap. The question this doc answers is not "should we build this" (the product vision already says yes) but **what should the Qiyrix version actually generate, how should it avoid Fullbloom's hallucination problem, and how big a slice is realistic for the current team.**

## Research Findings

### 1. Current codebase — what already exists to build on

This is the single most important finding: **aexa-ai already has most of the AI plumbing this feature needs**, built for a different current feature (per-site "AI generate risks" inside the Risk Register), and it is *safer* than Fullbloom's approach:

- `aexa-ai/app/services/company_sites_service.py` — given a company name, runs three Tavily web searches (`{company} locations sites list`, `branches offices locations`, `subsidiaries sites`) plus a targeted "how many sites does X have" query, feeds the **search snippets** (not parametric knowledge) into GPT-4-class extraction (`client.chat.completions.create(..., response_format={"type": "json_object"})`), and normalizes the result into `{sites, country, total_review, number_of_employe, sites_information[]}`. This is already a working **LLM + web-search-grounded generation** pipeline, wired to a real endpoint (`POST /company-sites` in `aexa-ai/app/api/v1/endpoints/company_sites.py`) — but it is **not currently called from aexa-server** (no reference to `company-sites` anywhere in `aexa-server/src`). It exists but is orphaned.
- `aexa-ai/app/services/risk_analysis_service.py` — given one site's profile (name, location, legal entity, activity, country, revenue, employee count), asks GPT (`settings.models.primary`) for 6–10 audit-style risks with scores, probability, velocity, trend, owner, in a strict JSON shape validated against `RiskAnalysisRequest`/`RiskItem` Pydantic models. This one **is** wired end-to-end: `aexa-server/src/app/modules/ai/ai.service.ts:analyze_site_risks_with_ai` calls it via `POST /risk_analysis`, and the frontend exposes it through `POST /analyze-site-risks`, used from the Risk Register to suggest risks for a site the user has already created.
- Critically, `analyze_site_risks_with_ai` has a code comment that is the single best piece of prior art for this ticket's UX question: *"this one does not persist anything — it returns the raw suggestions so the caller can review and selectively import them via the existing POST /risk route ..., rather than auto-creating Risk rows the user never asked for."* This is exactly the review-before-commit pattern this doc recommends below — it's already established practice in this codebase, just not yet applied to org-level onboarding.
- `Risk.ai_generated` and `Risk.is_edited` boolean columns already exist on the schema (`aexa-server/prisma/schema/risk.prisma`), and the Risk Register UI already renders a "🤖 IA" vs "Manuel" badge (`RiskRegisterPage.tsx:278`) — so the data model and UI already have a place to mark AI-originated records and track whether a human touched them since.
- No KRI-generation or Alert-generation AI service exists yet in aexa-ai — those would be new build, not reuse.
- Org creation itself has no backend today (see Problem Statement). Whatever gets built for #96 needs an org-create endpoint regardless of the AI question.
- Tenant identity: there is no separate "Organization" row that owns Site/Risk/Kri/Alert — those all hang off `org_account_id` → `Account` (the ROLE=ORGANIZATION account *is* the tenant). The newer `Organization`/`OrgMember` models (`organization.schema.prisma`, from issue #55) are a parallel membership/RBAC layer anchored to that same Account via `anchorAccountId`, not a replacement tenant root. Any onboarding flow has to create an `Account(role=ORGANIZATION)` first, then optionally the `Organization`/`OrgMember` scaffolding on top.
- `OrganizationProfile` (`organization_profile.schema.prisma`) already has `organizationName`, `organizationLocation`, `organizationDescription`, `organizationWebsite` — but **no `sector` or `country` field**, and no structured field for "what sector/country did zero-input analysis use," which matters for re-running/auditing the AI call later.

### 2. Fullbloom precedent

`full-bloom-app/src/features/onboarding/pages/OnboardingPage.tsx` (325 lines) is the reference UI: a single-screen form (company name required, sector/country optional) that on submit shows a **7-step fake progress list** (`ANALYSIS_STEPS`, each fired by a hardcoded `setTimeout` — 800ms apart, entirely disconnected from what the backend is actually doing) while a single call to `analyzeCompany()` runs in the background. When the call resolves, the page does eight sequential Supabase inserts directly into `organizations`, `sites`, `risks`, `risk_links`, `kris`, `alerts`, `audit_engagements`, `compliance_obligations` — **no review step, no diff, no way to reject or edit anything before it lands** — then redirects to `/dashboard`. If the AI call fails partway, nothing has been inserted yet (it fails before any insert block runs), but there's no transaction wrapping the eight inserts themselves, so a failure between insert #3 and #4 leaves a partially-seeded org with no cleanup path.

`analyzeCompany()` calls a Supabase edge function (`supabase/functions/ai-analyze/index.ts`, 649 lines) that is worth reading in full because it is a cautionary tale, not just a template to copy:

- The system prompt ("ARIA") instructs a **pure-knowledge** model call (Gemini 2.5 Pro, no search tool, no RAG) to name real subsidiaries, real site addresses, and — most alarmingly — to cite **exact legal articles** per country ("Art. L4121-1 Code du travail," "D.Lgs. 81/2008 Art. 28," etc.) and tag every site with a `discoverySource` like `"[Tier A] Source — détail"` implying it consulted a specific national corporate registry. It did not; there is no tool call, no `fetch`, no search API anywhere in this function. The model is being asked to fabricate citations that *look* verifiable, which is a worse failure mode than an unsourced guess: a CRO/CAE reading "[Tier A] RCS via Infogreffe — détail" has no way to tell it's invented without checking Infogreffe themselves.
- The "anti-hallucination" section ("COUCHE 3 — RÈGLES ANTI-HALLUCINATION," lines 42–47: "INTERDICTION ABSOLUE d'inventer un site...") is instruction-only — asking the model not to hallucinate does not stop it from hallucinating; it has no grounding mechanism backing the instruction up.
- There is a real, useful pattern buried in here though: `collectCoverageIssues()` (lines 400–486) runs a **structural** self-check after the first LLM call — minimum site count, every site has risks in required categories, every risk has a `sourceInfo` string, every country has a national-law-cited compliance obligation — and if it fails, re-prompts the model once with the specific gaps listed ("CORRECTION OBLIGATOIRE... 1. Nombre de sites insuffisant..."). This is a legitimate retry-on-validation-failure pattern (matches the CDC spec's "retry with corrective prompt" description), but note what it checks: *completeness of shape*, not *factual accuracy*. A hallucinated legal citation that has the right shape (`"[Tier X] | Loi Art. N"`) passes this check fine.
- Volume targets are aggressive and arguably counter-productive for trust: "40-80 risques minimum," "15-30 audits," "15-30 obligations conformité," explicitly instructing the model "NE PAS LIMITER L'OUTPUT — ÊTRE EXHAUSTIF." Forcing an LLM to hit a hard minimum count is a well-known hallucination amplifier — if the model runs out of real signal, it fabricates to hit the quota rather than returning fewer, better-grounded items.

**Net assessment of Fullbloom's approach:** the UX shape (single input, animated wait, land on populated dashboard) is a reasonable product goal, but the generation approach underneath it is not something to port as-is. It would put fabricated legal citations in front of CROs and CAEs with no review gate.

### 3. CDC spec precedent

`/tmp/cdc-spec.txt` describes "Zero-Input Intelligence" (§1.1, §1.3) as the platform's core differentiator: company name in, complete analysis in <30s, combining (1) the model's own sectoral/geographic knowledge, (2) real-time data from 60+ connected external APIs, (3) internal algorithms (PageRank, Monte Carlo, clustering). Note that this is explicitly a **hybrid** design (parametric knowledge *plus* live external sources), not the pure-knowledge approach Fullbloom's edge function actually implements — the CDC spec's vision is more defensible than Fullbloom's shipped code.

§7.1 ("Module Onboarding Intelligence") lays out the target pipeline as six timed steps: (1) company enrichment via a structured Claude prompt, 3s; (2) parallel collection across 60+ external APIs with per-source 4s timeout and cosine-similarity relevance filtering, 5s; (3) PageRank calc on a Neo4j graph, 1s; (4) Monte Carlo EBITDA simulation (10,000 scenarios), 2s; (5) content generation (audit templates, findings, compliance obligations, narrative report), 4s; (6) atomic Postgres persistence + Kafka event + 15-min Redis cache, 0.5s. Total P95 target: <30s end-to-end for a company that today has zero sites, zero risks, zero KRIs, zero connectors, zero compliance obligations, and zero audit plan.

The spec's own prompt-engineering guidance (just above §7.2) is worth keeping regardless of scope: a 3-part structured prompt — (1) role context ("CRO + CFO + CAE expert"), (2) strict JSON schema instructions, (3) consistency rules — with the returned JSON **Pydantic-validated before persistence**, and automatic retry with a targeted correction prompt on parse failure. This matches the pattern aexa-ai already uses in `risk_template_service.py` and `risk_analysis_service.py` (Pydantic `model_validate_json`, `clean_llm_response` stripping markdown fences) — so no new infrastructure pattern is needed, just extending an existing one.

`POST /api/v1/onboarding/analyze` (§8, line ~1567) is specified with `Body: company_name, sector, country, sites[]` and scope `org:write` — i.e. sites can optionally be supplied up front rather than only discovered.

**Phasing reality check:** §11.2 places "Phase 1 — Zero-Input Core" (onboarding + Claude integration + risk register + basic KRI + CEO dashboard) at **7 weeks**, but that follows a 5-week "Phase 0 — Foundation" that assumes things Qiyrix does not have today: Neo4j graph infra, a PageRank/clustering compute service, a 7-microservice architecture (api-gateway, risk-core, intelligence, data-collector, audit-engine, report-generator, notification), Kafka event bus, Clerk.com SSO/MFA, and — separately, in Phase 3 — the 60+ external data connectors that Phase 1's own step 2 depends on for "collecte 60+ sources mondiales." **Phase 1 as specced is not actually buildable standalone**; it presupposes infrastructure (Neo4j, Kafka, the connector layer) that the roadmap itself doesn't deliver until Phases 0 and 3. This is flagged explicitly in Open Questions below — the CDC spec's 7-week estimate is not usable as-is for scoping Qiyrix's version.

### 4. External research — real-world zero-input / AI onboarding patterns

**Compliance-SaaS precedent (Vanta / Drata / Secureframe).** None of these three actually do "company name → fully generated compliance program" onboarding. Vanta optimizes for fast connector-based setup (integrations autodetect infrastructure and map it to controls, but the *framework selection and control set* is still user-chosen, not AI-inferred from company identity alone). Secureframe leans on white-glove human-guided setup rather than an autonomous AI pass, explicitly to "reduce the number of decisions you have to make cold." Drata automates evidence collection and risk mapping *after* the org and framework are established, not as a zero-input first step. Across all three, the emerging norm for AI-in-compliance-workflows is "AI drafts, human verifies before it's load-bearing" — not autonomous generation-to-production. [Sprinto: Secureframe vs Vanta vs Drata](https://sprinto.com/blog/secureframe-vs-vanta-vs-drata/), [Drata: Secureframe vs Vanta vs Drata](https://drata.com/learn/compare/secureframe-vs-vanta-vs-drata), [Silent Sector comparison](https://silentsector.com/blog/drata-vs-vanta-secureframe). This is a meaningful signal against faithfully copying Fullbloom's "land straight on a populated dashboard" pattern — the category leaders don't trust AI output that far without a checkpoint, and Qiyrix's own `analyze_site_risks_with_ai` code comment already independently arrived at the same conclusion.

**LLM hallucination/grounding literature, applied to this problem.** General findings: hallucination rates for good current models on knowledge-intensive tasks are meaningfully above zero even at the low end (industry reporting cites figures from well under 1% up to 30%+ depending on model and task), and retrieval-augmented generation is the standard mitigation — grounding the model in retrieved, citable source text measurably reduces fabrication versus asking it to answer from parametric memory alone. [Glean: contextual grounding](https://www.glean.com/perspectives/when-llms-hallucinate-in-enterprise-contexts-and-how-contextual-grounding), [Branch8: hallucination mitigation strategies](https://branch8.com/posts/ai-model-hallucination-risk-mitigation-strategy-apac-enterprise-guide). Applied here: a company's *identity* (does it exist, what sector, roughly what size, HQ country) is checkable against public sources (registries, corporate sites, LinkedIn) and should be retrieval-grounded, the way `company_sites_service.py` already does with Tavily. A *generic* starter risk taxonomy for "a mid-size manufacturer in France," by contrast, does not need retrieval — industry-standard risk categories (COSO ERM's four categories; ISO 31000's process; NIST CSF for cyber) are stable, well-represented in any base model's training data, and don't require fresh grounding to state correctly. The danger zone is specifically **company-specific factual claims** (real subsidiary names, real site addresses, real legal citations with article numbers) generated without retrieval — exactly what Fullbloom's edge function does and what Qiyrix should not replicate ungrounded.

## Alternatives Considered

### A. Generation approach (how the AI content gets produced)

| Approach | Trust / hallucination risk | Complexity | Cost | Notes |
|---|---|---|---|---|
| **A1. Pure LLM-knowledge** (Fullbloom's actual approach: one big prompt, no tools, ask for real subsidiary names + exact legal article citations) | **High.** Model fabricates plausible-looking specifics (site addresses, "[Tier A] source" tags, statute article numbers) with no way to distinguish real from invented without independent verification. Actively dangerous for a CRO/CAE audience whose job is trusting citations. | Low — one prompt call, already have the pattern in aexa-ai | Low (one LLM call, no external API spend) | Reject as the sole mechanism. Only acceptable for genuinely generic content (taxonomy labels, not facts). |
| **A2. LLM + web-search grounding** (extend `company_sites_service.py`'s Tavily pattern to also ground sector/HQ-country/employee-count claims, and optionally per-site risk context) | **Medium-low.** Claims are extracted from retrieved snippets rather than invented, and can carry a source URL for the reviewer to spot-check. Still not perfect — search results can be wrong, stale, or the extraction step can still slightly over-claim — but categorically better than A1, and it's what NIST/industry guidance recommends for knowledge-grounding. | Medium — already exists for company/site discovery in aexa-ai, needs extending and needs a Tavily budget/rate-limit story | Medium (Tavily search calls + LLM extraction calls per org) | **Recommended** for anything claiming to be a fact about *this specific company*. |
| **A3. Template-by-industry + light AI personalization** (maintain a curated starter risk/KRI library per sector — e.g. "Manufacturing," "Financial Services," "Healthcare" — each mapped to COSO ERM categories and common regulatory triggers (NIS2, GDPR, sector-specific), then use the AI only to pick the right template and lightly tailor wording to the company name/size) | **Lowest.** Nothing is fabricated — the risk taxonomy is human-curated and reviewed once, not generated per org. AI's job is classification + light rewrite, a much narrower and more verifiable task. | Medium — requires building and maintaining the template library (a real content investment, not just code) | Lowest (classification is cheap; no need to regenerate the whole register per org) | Strong candidate for the risk/KRI *baseline*, where "audit-grade generic starting point, editable" is the actual product need, not "provably true fact about this exact company." |

**Recommendation:** don't pick one exclusively — split by claim type, matching what the external research suggests:
- **Company identity fields** (sector, HQ country, rough size, discovered sites) → **A2**, grounded, because these are factual claims about a specific real entity and the infrastructure to do this safely (Tavily + extraction) already exists in aexa-ai, unused.
- **Starter risk register / KRIs** → **A3 as the backbone, A2 to enrich where grounding is cheap** (e.g., if a site's country is known, deterministically attach that country's well-known regulatory triggers — GDPR, local labor code category — rather than asking the LLM to invent the exact article number). This avoids the Fullbloom failure mode (fabricated statute citations) while still producing an org-specific-*feeling* register (site names, sector-appropriate categories) rather than a generic template dump.
- **Never**: unconstrained A1 for anything presented as a citable fact. If pure-knowledge generation is used at all (e.g. to draft a plausible risk *description* in prose), it must be visually distinguishable from grounded/templated content and never carry a fabricated source citation.

### B. Scope alternatives (how much the wizard asks for vs. infers)

1. **True zero-input** — company name only, exactly matching Fullbloom's form and the CDC spec's "seul le nom est obligatoire" principle. Maximizes the "wow" of the demo; maximizes hallucination surface because everything (sector, country, sites, risks) has to be inferred or discovered.
2. **Structured wizard, AI fills gaps** — collect company name + sector + HQ country + optionally a short site list up front (this matches the CDC spec's actual specified endpoint body: `company_name, sector, country, sites[]` — even the spec doesn't treat sector/country as AI-only in the API contract, just optional in the UI). AI is used to discover *additional* sites, generate the risk/KRI baseline, and fill in anything left blank. Meaningfully lower hallucination surface (sector and country, the two most consequential inputs for taxonomy selection, come from the user, not a guess) at a small UX cost (2-3 extra optional fields).
3. **Minimal-input + confirm-before-generate** — company name required; AI does a *lightweight* first pass (via A2, Tavily-grounded) to propose sector/country/sites, shows them to the user for confirmation/correction *before* running the expensive risk/KRI generation step. This is a middle ground: still feels close to zero-input, but catches "wrong company" or "wrong sector" mistakes (a common real risk when company names collide, e.g. multiple "Atlas Industries") before they propagate into 40+ generated risk records.

**Recommendation: option 3.** It preserves the "type a name, AI does the heavy lifting" pitch that's the actual product differentiator, while inserting exactly one cheap confirmation step before the expensive/consequential generation runs — cheap in both latency (the company/site discovery call is fast) and UX friction (one screen, pre-filled, edit-or-confirm). Option 1 has no error-correction point at all; option 2 loses some of the "zero-input" positioning for marginal safety gain over option 3.

## Recommended Approach

1. **Pipeline shape** (four stages, not Fullbloom's single opaque call):
   - **Stage 1 — Identify** (new): company name → Tavily-grounded lookup (extend `company_sites_service.py`) → proposed sector, HQ country, employee-count band, and discovered sites. Fast (~5-8s, matches the existing Tavily-call latency profile).
   - **Stage 2 — Confirm** (new, UI): show the proposal, let the user edit/accept/reject individual fields and individual discovered sites before anything is generated. This is the review gate option-3 scope requires.
   - **Stage 3 — Generate baseline** (extend existing): for each confirmed site, call the existing `/risk_analysis` pattern (A3-backbone/A2-enrichment per Alternative A) to produce a starter Risk set; derive 1-2 starter KRIs per risk category present (new, small AI service or deterministic mapping — see Open Questions); do **not** generate Alerts synthetically — Alerts should come from real signal (see Data Model section), so seed zero and let the alert pipeline populate them once it exists, or seed a single "Welcome — no alerts yet" placeholder at most.
   - **Stage 4 — Review-before-commit** (new, UI, mandatory): everything from Stage 3 is shown as an editable, checkbox-selectable list — matching the exact pattern `analyze_site_risks_with_ai` already established ("returns raw suggestions ... caller can review and selectively import"). Nothing is written to Postgres until the user clicks a final "Create organization" action. Every persisted row gets `ai_generated: true` (field already exists on `Risk`) and, ideally, a per-record source annotation for the grounded fields.

2. **Why this over faithfully copying Fullbloom:** Fullbloom's version writes directly to the database after a cosmetic animation with zero user checkpoint, using an ungrounded prompt that fabricates legal citations. Given the audience (CROs, CFOs, CAEs — people whose job is catching exactly this kind of false-precision), shipping that pattern as-is is a trust liability, not just a quality gap. The codebase's own prior art (`analyze_site_risks_with_ai`'s comment) and the external research (compliance-SaaS category norm of "AI drafts, human verifies") both point the same direction: keep the zero-input *pitch*, add a review gate the Fullbloom version doesn't have.

3. **Hallucination/trust posture, explicitly:**
   - Every AI-touched record carries `ai_generated: true` (already exists on `Risk`) — extend this flag to `Site` (currently missing) and to whatever new KRI-seeding path is built, so the UI can always visually distinguish AI-sourced from human-entered content, matching the existing "🤖 IA" badge convention in `RiskRegisterPage.tsx`.
   - Grounded claims (sector, country, discovered sites) should carry the retrieval source so a reviewer can verify it, not just trust it — extend `Site`/`Risk`'s existing `source_info` field (already on `Risk`, not yet on `Site`) to carry this rather than inventing a new field.
   - Never surface a fabricated legal citation. If a compliance/regulatory angle is wanted later, gate it behind actual grounding (a real regulatory database lookup or Tavily search against a known official source), not a bare LLM claim — this is explicitly a scope-cut from the CDC spec's compliance-register ambitions for Phase 1, not a nice-to-have to defer casually.

## Data Model Implications

- **Org creation, currently missing entirely:** need a real `POST /organization` (or equivalent) flow in aexa-server creating `Account(role=ORGANIZATION)` + `OrganizationProfile`. Whether it also creates an `Organization`/`OrgMember` row (issue #55's model) at the same time is a product question — likely yes, so the creating admin/owner lands as `OrgRole.ADMIN` on day one, but that's a call for whoever owns #55's rollout sequencing, not this ticket alone.
- **`OrganizationProfile`** needs two new fields to make the AI call auditable/re-runnable: `sector: String?`, `country: String?` (currently absent — the model only has name/logo/location/description/website/phone). Worth also storing the raw Stage-1 AI proposal (or at least a pointer/timestamp) somewhere for support/debugging — the CDC spec's own "cache 15min" and audit-trail instincts are reasonable here even without the full Kafka/Redis infra.
- **`Site`** needs an `ai_generated: Boolean @default(false)` field to match `Risk`'s existing convention (currently `Site` has no such flag) and a `source_info: String?` field to carry the Tavily-derived discovery citation, mirroring `Risk.source_info`.
- **`Risk`** already has everything needed (`ai_generated`, `is_edited`, `source_info`) — no schema change required for the risk baseline itself.
- **`Kri`** has no `ai_generated` flag today. If AI-seeded starter KRIs ship (recommended, see Effort Estimate), add one for the same review/trust-labeling reason as Risk/Site.
- **`Alert`** already has `ai_generated`, but per the Recommended Approach, onboarding should not synthesize alerts from nothing — seed zero (or a single non-`ai_generated` welcome notice) and let the real alert pipeline (whatever ingests actual signal) populate it later. Generating fake "alerts" at onboarding to make the dashboard look busy would be actively misleading.
- No schema change needed to reuse the existing `Notification` model (`ai.prisma`) for progress/completion signaling if onboarding is made async (see Open Questions on latency).

## API Endpoints

Split across aexa-server (orchestration, persistence, auth/org-scoping) and aexa-ai (LLM/search calls), matching the existing division of responsibility in this codebase (aexa-server never calls OpenAI/Tavily directly; it always proxies through aexa-ai with the shared `AI_INTERNAL_SECRET`).

**aexa-ai (FastAPI, extend existing `app/api/v1/endpoints/`):**
- `POST /company-sites` — **already exists**, currently orphaned (no caller in aexa-server). Reuse as-is for Stage 1's site-discovery half.
- `POST /company-identify` *(new, small)* — thin wrapper around the same Tavily+extraction pattern as `company_sites_service.py`, but scoped to sector/HQ-country/employee-band rather than site list (or fold into a combined `/company-profile` endpoint that returns both — simpler than keeping two near-duplicate Tavily-search flows). Returns proposed values with per-field source snippets for the confirm screen.
- `POST /risk_analysis` — **already exists and already wired**, reuse per-site as-is in Stage 3.
- `POST /kri-baseline` *(new)* — given a confirmed Risk list (or risk categories), return 1-2 starter KRI suggestions per risk with plausible unit/threshold/target — likely template-driven (Alternative A3) rather than a fresh LLM call per risk, to control cost and hallucination surface on numeric thresholds specifically (a fabricated "alert_threshold" is arguably worse than a fabricated prose description, since it silently governs when the platform claims something is wrong).

**aexa-server (Express, extend `src/app/modules`, likely a new `onboarding` module rather than overloading `ai` or `account`):**
- `POST /organization` *(new — currently does not exist at all)* — creates `Account(role=ORGANIZATION)` + `OrganizationProfile`. Required regardless of the AI question; today `AdminOrganization.tsx`'s modal has nothing to call.
- `POST /onboarding/identify` *(new)* — proxies to aexa-ai's company-profile lookup, `auth('ADMIN')` or whatever role is allowed to create orgs (today, implicitly admin-only per `AdminOrganization.tsx`'s location under `dashboard/admin/`). Returns the Stage 1 proposal for the Stage 2 confirm screen. Does not persist anything.
- `POST /onboarding/generate` *(new)* — takes the Stage 2-confirmed profile (sector, country, sites[]), fans out to `/risk_analysis` per site (+ `/kri-baseline`), returns the full Stage 3 draft. Still does not persist anything — matches `analyze_site_risks_with_ai`'s existing "don't persist, return for review" contract.
- `POST /onboarding/commit` *(new)* — takes the org profile + the user's edited/selected subset of the Stage 3 draft, and atomically creates the Organization/Account/Site/Risk/Kri rows in one Prisma transaction. This is the only step that writes anything. Wrap in `prisma.$transaction` to avoid Fullbloom's partial-insert failure mode (its eight sequential un-transacted Supabase inserts).

## UI/Workflow

1. **Entry screen** — company name (required) + sector/country (optional, pre-fillable, matches CDC spec's actual endpoint contract even though the UI treats them as optional). Single "Analyze" action, replacing/extending `AdminOrganization.tsx`'s current fake modal.
2. **Stage 1 result / confirm screen** (new, mandatory per the review-gate recommendation) — shows proposed sector, HQ country, size band, and a checkbox list of discovered sites (from `/company-sites`), each with its `discoverySource`-style citation visible so the reviewer can see *why* the AI thinks that site exists. User can edit any field, uncheck sites, or add a site manually. "Continue" is disabled until at least the org-level fields are confirmed.
3. **Progress state while Stage 3 runs** — unlike Fullbloom's `setTimeout`-driven fake step list, tie the displayed steps to real backend progress if the latency is worth showing incrementally (per-site risk generation is naturally chunkable — "Analyzing risks for {site}..." can update as each site's `/risk_analysis` call returns, since Stage 3 fans out per confirmed site anyway). If latency ends up low enough (single-digit seconds for a 1-3 site org), a simple spinner is honest and sufficient — don't build fake pacing.
4. **Stage 3 review screen (the important one)** — every generated Risk (and KRI) shown as an editable, individually checkbox-selectable card, grouped by site, each visibly tagged AI-generated (reusing the existing "🤖 IA" convention). User can edit text/scores inline, uncheck items they don't want, and must take an explicit "Create Organization" action to commit — nothing lands in the database from viewing this screen alone. This directly mirrors the existing Risk Register's "AI suggests, human imports selectively" pattern, just applied at org-creation scope instead of single-site scope.
5. **Post-commit** — land on the new org's dashboard, now populated, with an org-level banner ("N risks and M KRIs were AI-generated during setup — review recommended") rather than pretending the content is equivalent to a human-audited baseline.

## Open Questions for Omar

1. **Who can trigger this?** Today org creation lives under `dashboard/admin/`, implying platform-admin-only (a Qiyrix employee creates the tenant). Is zero-input onboarding meant for that admin flow, or for **self-serve signup** (a prospect creates their own org)? These have very different trust/abuse profiles — self-serve means an unauthenticated or freshly-authenticated user is triggering paid Tavily+LLM spend per attempt, which needs rate limiting/CAPTCHA-adjacent protection that admin-triggered onboarding doesn't.
2. **Phasing realism, explicitly:** the CDC spec's 7-week "Phase 1 — Zero-Input Core" estimate assumes Phase 0 infra (Neo4j, Kafka, the 7-microservice split, Clerk SSO) and Phase 3's 60+ connector layer are already in place — neither exists in the current aexa-server/aexa-frontend/aexa-ai stack. Treating "7 weeks" as this ticket's estimate would be a scoping error inherited from a roadmap written for a different starting point. Does Omar want a from-scratch estimate against the *current* stack (see Effort Estimate below), or is there appetite to actually build toward the CDC spec's microservice/Neo4j architecture first, in which case #96 is blocked on much larger infra work, not a frontend/backend feature ticket?
3. **PageRank/Monte Carlo — in or out of MVP?** The CDC spec ties Zero-Input Core to PageRank scoring and Monte Carlo EBITDA simulation. Current `Risk.pagerank_score` exists as a nullable Int column but nothing computes it (no Neo4j, no graph engine anywhere in aexa-server or aexa-ai). Confirm this is out of scope for a first cut — the MVP below assumes so — since building a graph-based scoring engine is an order of magnitude bigger than the onboarding UX itself.
4. **Tavily/OpenAI cost ownership and rate limiting per onboarding attempt:** `company_sites_service.py` already fires 4 Tavily calls per invocation; Stage 3 adds one `/risk_analysis` call per confirmed site. For a 10-site org that's ~14 external calls per onboarding attempt, plus retries. Is there an existing budget-alert mechanism to hook into, or does this need new metering? (The CDC spec flags this exact risk in §11.3 — "Coûts Claude API non maîtrisés" — but no mitigation currently exists in aexa-ai beyond `settings.llm.timeout_seconds`.)
5. **KRI-baseline generation approach** (template-driven vs. per-risk LLM call) is left open in this doc pending a decision on acceptable numeric-hallucination risk for `alert_threshold`/`target_value` — worth a short spike before committing either way.
6. **Does `Organization`/`OrgMember` (issue #55's model) get created at onboarding time**, with the creating user as `ADMIN`, or does onboarding only touch the legacy `Account`-as-tenant model and #55's layer gets backfilled separately like existing accounts are? Affects whether `POST /organization` needs to also write `OrgMember`.

## Effort Estimate

**Full CDC-spec parity (Neo4j/PageRank, Monte Carlo, 60+ connectors, audit-plan/compliance-register generation): out of scope for a T-shirt estimate here** — that's the multi-quarter Phase 0+1+3 CDC roadmap, not a single ticket, per Open Question 2.

**Cut-down MVP matching this doc's Recommended Approach: L (large single-ticket-cluster, roughly 3-4 weeks for one full-stack engineer, more realistically split across 2 people — one aexa-ai/Python, one aexa-server+frontend/TS — for ~2-2.5 weeks in parallel):**

- aexa-ai: wire up `/company-sites` caller, add `/company-identify` (or combined `/company-profile`), add `/kri-baseline` (template-driven) — **S-M**, mostly extending existing patterns.
- aexa-server: `POST /organization` (net-new, needed regardless), `onboarding` module (identify/generate/commit, transactional commit) — **M**, mostly plumbing given `/risk_analysis` proxy pattern already exists to copy.
- aexa-frontend: replace `AdminOrganization.tsx`'s fake modal with the real create flow, build the 3-4 screen wizard (entry → confirm → progress → review-and-commit) — **M-L**, this is genuinely new UI, the biggest single piece.
- Schema: add `ai_generated`/`source_info` to `Site`, `sector`/`country` to `OrganizationProfile`, optionally `ai_generated` to `Kri` — **S**, straightforward additive migration.

What's deliberately cut from the "full vision" for this MVP: PageRank/graph scoring, Monte Carlo, alert auto-generation, audit-plan generation, compliance-obligation generation, the 60+ external connector layer. Those remain real product ambitions per the CDC spec but are separate, larger efforts that shouldn't gate shipping a working, trustworthy version of "type a company name, get a reviewable starter risk register" — which is itself already a significant improvement over the current zero-functionality state.
